# WindWoods SEO・LLMO改善記録と継続運用ガイド

以下は、WindWoodsのリポジトリや過去の会話を見られない第三者でも、調査の前提、発見した問題、判断理由、実装内容、実測結果、残課題、次回の測定方法まで理解できる形に整理した記録です。

記録日：2026年8月21日\
対象サイト：https://windwoods-stayble.com/\
対象事業：株式会社Staybleが運営する民泊・バケーションレンタル清掃管理サービス「WindWoods」

# 1. 今回のSEO・LLMO改善記録

## 前提

WindWoodsは、北海道の民泊・バケーションレンタル向けに、客室清掃だけでなく、リネンサプライ、消耗品管理、ゴミ回収、定型写真による報告管理まで提供する清掃管理サービスです。

サイトはGitHub Pages上の静的サイトとして公開され、独自ドメイン `windwoods-stayble.com` を使用しています。

公開対象は次の6ページです。

- トップ
- 札幌
- 千歳
- 小樽
- 北広島
- 恵庭

各地域ページは単なる地域名差し替えページではなく、地域固有の需要、地区名、供給体制、事業上の背景を持つページとして構成されています。

会社・料金・サービス・地域に関する事実は、社内で確定した情報だけを使用し、実績、効果、地域別件数などを推測で追加しないことを前提としました。

## 今回の目的

この改善は、メタタグを一度設定して終わる作業ではありません。

目的は次の4点です。

1. Google、Bing、Yahooなどの通常検索で、地域名を含む非指名検索の露出を増やす。
2. AI Overview、AI Mode、Bingの生成AI検索などが、運営会社、サービス、対応地域、料金、特徴を正確に理解しやすい状態にする。
3. 検索結果から訪問した利用者が、スマートフォンで速くページを開き、必要な情報を確認し、問い合わせまで進みやすい状態にする。
4. 変更後の効果を、検索順位だけでなく、表示回数、クリック、問い合わせ、AI検索での引用、ページ速度に分けて継続測定できる状態にする。

最終的な目標は、各検索媒体で地域の民泊清掃を探す利用者にとって最有力候補として表示されることです。ただし、順位は競合、被リンク、地域情報、検索需要、季節性、検索エンジン側の再評価にも左右されるため、サイト内の変更だけで最上位を保証するものではありません。

## 前回実装から今回監査まで

サイトの主な履歴は次のとおりです。

- 2026年6月25日：サイト公開、Search Console確認、札幌ページとsitemapを公開
- 2026年7月4日：対応地域を現在の札幌・千歳・小樽・北広島・恵庭へ更新
- 2026年8月2日：全環境共通のファビコンを実装
- 2026年8月21日：今回のSEO・LLMO監査、改善、公開後実測を実施

地域構成の最終更新から48日、ファビコン更新から19日が経過した時点を今回の基準日としました。

新しいLPから実際に問い合わせは発生していました。

一方で、旧LPほど強い上位表示には至っておらず、地域名を含む非指名検索では競合サイトが優勢でした。

2026年8月21日に、個人の検索履歴に依存しない公開検索サンプルで次の5クエリを確認しました。

|---|---:|
| 札幌 民泊 清掃 | 返却された主要結果内で未検出 |
| 千歳 民泊 清掃 | 返却された主要結果内で未検出 |
| 小樽 民泊 清掃 | 返却された主要結果内で未検出 |
| 北広島 民泊 清掃 | 返却された主要結果内で未検出 |
| 恵庭 民泊 清掃 | 返却された主要結果内で未検出 |

非指名5クエリの検出は0件／5件でした。

ブランド名やサイト指定の検索では、新ドメインのトップと札幌ページを確認できました。そのため、サイトがまったく発見されていないのではなく、ブランド検索では認識され始めている一方、一般的な地域検索での評価が不足している状態と判断しました。

## 調査方法

今回の監査は、次の5方向に分けて行いました。

### 1. 検索エンジンから見える状態

- 公開URLが200で応答するか
- HTTPS、wwwあり・なし、正規ホストが統一されているか
- title、description、canonical、robots指定が正しいか
- robots.txtとsitemap.xmlがクロールを妨げていないか
- 各ページのH1が検索対象地域を明示しているか
- トップと地域ページが相互に内部リンクされているか
- OGP画像がページ内容と一致しているか
- 旧ドメインから新ドメインへ301リダイレクトされているか

### 2. 検索エンジンとAI検索が理解できる状態

- 運営会社、ブランド、サービス、対応地域の関係が一貫しているか
- 主要情報がJavaScript実行前のHTML本文に存在するか
- 地域ごとの事実と共通サービス情報を区別できるか
- 構造化データが実際の事業形態と一致しているか
- 料金、サービス範囲、対応地区、判断条件が明文化されているか
- 利用者が実際に尋ねる質問への回答が可視本文にあるか

### 3. 表示速度とモバイル体験

- Lighthouse mobileのPerformance、SEO、Accessibility、Best Practices
- FCP、LCP、TBT、CLS
- 初期表示時の転送量
- LCP画像の容量と取得優先度
- 外部フォント、予約サービス、画像が初期表示を阻害していないか
- スマートフォンで見出しやCTAが画面外へはみ出さないか

### 4. 問い合わせまでの計測可能性

- 概算試行と正式な問い合わせを区別しているか
- 検索、広告、参照サイト、直接流入を後から区別できるか
- 最初に見たページと地域を保存できるか
- UTMパラメータや広告クリックIDを問い合わせと結び付けられるか
- 個人情報を不要に追加保存していないか

### 5. 継続運用の再現性

- 画像を同じ条件で再生成できるか
- SEO要件を機械的に再監査できるか
- 更新後にBing系検索サービスへ通知できるか
- 1か月後に同じ期間・同じ指標で比較できるか

## 調査開始時点ですでに良かったこと

監査では、未実装項目だけでなく、すでに成立している基盤も分けて確認しました。

- 全6ページに固有のtitleとdescriptionがあった。
- canonicalは独自ドメインの正規URLを指していた。
- robotsは `index,follow` で、robots.txtも全体を許可していた。
- sitemapに公開中の6ページが登録されていた。
- Google Search Consoleの所有権確認情報が設置されていた。
- 全6ページで、ルート配置された同一のファビコン一式を絶対パスで参照していた。
- 地域ページには地域固有の本文、地区名、ストーリーがあった。
- トップと各地域ページの内部リンクがあった。
- 料金表、概算計算、問い合わせフォームが静的HTMLとJavaScriptで実装されていた。
- 概算試行だけでは情報を送信せず、正式な問い合わせ時だけ送信する設計になっていた。

したがって、今回の課題は「SEOが何もない」ことではなく、基本設定はあるものの、検索意図との一致、事業実態の表現、速度、計測、旧ドメイン移行が不足していることでした。

## SEO本監査より前に解決した検索表示上の問題

### ファビコンがなく、媒体ごとに表示が統一されていなかった

当初、検索エンジンやブラウザーが取得できる正式なファビコン一式がサイト側にありませんでした。

確認されていた現象は次のとおりです。

- Chromeでは、ヘッダー画像の一部が代替サムネイルのように表示されることがあった。
- Bingではファビコンを取得できず、Yahooでも同様の未取得状態が想定された。
- 旧アイコンは `assets/` 内に断片的に存在していたが、標準的に取得される `/favicon.ico` と、全ページ共通の明示指定がなかった。

原因はブラウザー固有の不具合ではなく、サイトルートにクロール可能な標準ファイルがなく、HTMLからの参照も統一されていないことだと判断しました。

対策では、まず画像生成によるラフを1点作り、黒地に重厚感のあるゴールドのWというトーンの基準だけを決めました。AI生成ラスターは本番アイコンには使わず、太いWを幾何学的に清書したSVGをマスターにしました。

マスターの基本色は、ブランド規定に合わせた黒 `#050505` とゴールド `#d3b965` です。高解像度マスターではゴールドの濃淡を使い、16px、32px、48px向けには単色化して、縮小時につぶれない構成にしました。

追加したマスターと派生ファイルは次のとおりです。

- `assets/branding/favicon-concept-reference.png`：画像生成によるトーン参考
- `assets/branding/favicon-master.svg`：編集元となるベクターマスター
- `assets/branding/favicon-master-1024.png`：黒背景込みの1024×1024書き出し
- `/favicon.ico`：16px、32px、48pxを内包
- `/favicon.svg`：小サイズ用の単色ゴールド版
- `/favicon-96x96.png`
- `/apple-touch-icon.png`：180×180、余白付き
- `/web-app-manifest-192x192.png`
- `/web-app-manifest-512x512.png`
- `/site.webmanifest`

トップ、札幌、千歳、小樽、北広島、恵庭の全6ページへ、次の絶対パス指定を統一して追加しました。

```html
<link rel="icon" href="/favicon.ico" sizes="any">
<link rel="icon" type="image/svg+xml" href="/favicon.svg">
<link rel="icon" type="image/png" sizes="96x96" href="/favicon-96x96.png">
<link rel="apple-touch-icon" href="/apple-touch-icon.png">
<link rel="manifest" href="/site.webmanifest">
```

manifestの `name` と `short_name` はWindWoods、`theme_color` と `background_color` は `#050505` に統一しました。robots.txtがアイコンを妨げていないこと、全ページが同じファイルを参照すること、ルート絶対パスで解決することも確認しました。

書き出しは `scripts/generate-favicons.mjs` で再現でき、マスターSVGからPNG、SVG、ICO、manifestを一括生成します。

この変更によって、各媒体が同じWレターマークを取得できる技術条件は整いました。ただし、検索結果のファビコンは各検索エンジンの再クロールとキャッシュ更新後に反映されるため、設定直後の表示変更は保証されず、数日から数週間かかる場合があります。

## 発見した主な問題

### 非指名の地域検索で主要結果に出ていなかった

ブランド検索では発見されていましたが、地域名と民泊清掃を組み合わせた5クエリでは主要結果に検出されませんでした。

この差から、インデックスの有無よりも、一般検索に対する関連性、ページ評価、旧サイトからの評価継承、地域事業としての外部シグナルが課題と考えました。

### 旧Wixドメインの評価が新サイトへ移っていなかった

旧LPのドメイン `ww-sapporo-minpaku.com` は、Wixの接続案内または404相当の状態で、新ドメインへのサーバー側301リダイレクトを確認できませんでした。

新ドメインのDNSはGitHub Pagesへ正しく接続されていました。そのため、新サイトの接続障害ではなく、旧URLから新URLへの移行処理がないことが問題でした。

Gmailフッターから旧Wix画面へ移動した事象は、表示文字列と実際のリンク先が異なっていたことが原因で、メール設定の修正により解決しました。ただし、検索エンジンや外部サイトが保持する旧URLの評価継承は別問題です。

旧トップから新しい札幌ページへ301を設定しない限り、旧LPが持っていた可能性のある被リンク、履歴、指名シグナルは自動的には新サイトへ集約されません。

### LighthouseのSEO点数は高いが、実表示が非常に遅かった

変更前の公開トップは、Lighthouse SEOが100である一方、Performanceは63、LCPは19.5秒、初期転送量は約3.1MBでした。

札幌ページもSEOは100でしたが、Performance 68、LCP 10.4秒、転送量約2.05MBでした。

つまり、メタタグの形式的な存在は評価されていても、利用者が主要内容を見るまでの時間が長い状態でした。

主な原因は次のとおりです。

- トップ背景PNG：約1.7MB
- ヘッダーのWロゴPNG：約688KB
- 地域ヒーロー画像とリネン画像がJPEGのまま
- 外部Webフォントが初期描画と再レイアウトを発生させる
- TimeRexの埋め込みJavaScriptを問い合わせ前から読み込む
- CSS背景のLCP画像がHTMLから発見しにくい

### 地域ページのH1に地域名が入っていなかった

各地域ページのtitleとdescriptionには地域名がありましたが、H1は5ページとも共通の「民泊清掃代行サービス」でした。

ページ本文には地域情報があるものの、ページ最上位の見出しだけでは、検索エンジン、AI検索、利用者のいずれにも対象地域が即座に伝わりにくい状態でした。

### すべてのページが同じ千歳向けOG画像を使用していた

トップ、札幌、千歳、小樽、北広島、恵庭の全ページが、千歳向けの文言を含む同一OG画像を参照していました。

OGPは通常検索の直接的な順位要因ではありませんが、メール、SNS、メッセージ、検索サービスのプレビューで内容を誤認させ、共有時のクリック率や信頼性を損なう可能性があります。

### 地域ページが別々のLocalBusinessとして記述されていた

5つの地域ページすべてにLocalBusiness／CleaningServiceが設定され、地域ごとに別の事業体が存在するような構造になっていました。

実態は、株式会社Staybleという1社が、WindWoodsという1サービスを5地域へ提供する出張型サービスです。

実在する別拠点の住所、電話番号、営業時間がない地域まで別店舗として記述すると、検索エンジンやAI検索が会社とサービスの関係を誤解する可能性があります。

### 利用者が判断するためのFAQがなかった

本文には多くの情報がありましたが、対応地区、料金、リネン、品質管理、地域ごとの供給体制などが、質問と回答の形では整理されていませんでした。

AI検索向けに特別な隠し文章を置くのではなく、利用者が実際に確認したい内容を、可視本文で明確に答える必要がありました。

### 問い合わせが来ても流入元を比較できなかった

問い合わせは発生していましたが、次の情報を問い合わせ単位で確認できませんでした。

- 最初に見たページ
- 最初に見た地域
- Google、Bing、Yahoo、広告、紹介サイト、直接流入の区別
- UTM source、medium、campaign
- Google広告とMicrosoft広告のクリックID

この状態では、問い合わせが増減しても、どの検索媒体、どのページ、どの施策が寄与したかを判断できません。

### Bing・Yahooへの更新通知手段がなかった

sitemapはありましたが、公開や大幅更新の直後に、BingおよびIndexNow参加検索サービスへ変更URLを通知する仕組みがありませんでした。

Yahoo検索はBing系の情報と連動する場面があるため、GoogleだけでなくBing側の発見・再クロールも独立して管理する必要があります。

### sitemapに検索エンジンが利用しない指定が残っていた

sitemapには `changefreq` と `priority` が記載されていました。

現在のGoogleではこれらよりも、意味のある変更時に正確な `lastmod` を記録することが重要です。

### 所有者データを取得できる接続がなかった

Search Consoleの確認タグはありましたが、作業環境にはSearch ConsoleまたはBing Webmaster Toolsへサインイン済みのブラウザー、API資格情報、エクスポートCSVがありませんでした。

そのため、クリック、表示回数、CTR、平均掲載順位、生成AI引用数を推測で埋めず、未取得として扱いました。

## 改善仮説

実装前に、変更と期待する結果を次のように分けました。

| 仮説 | 実施内容 | 主な評価指標 |
|---|---|---|
| 地域名と検索意図をH1・本文・FAQで一致させると、非指名表示が増える | 地域名入りH1、地域固有FAQ | 非指名表示回数、地域クエリ掲載順位 |
| 会社・サービス・地域の関係を正確にすると、検索とAIが理解しやすくなる | Organization＋Service＋areaServed | インデックス、AI引用、ページ別表示 |
| 初期表示を軽くすると、モバイル体験とクロール効率が改善する | WebP、SVG、外部フォント削除、TimeRex遅延読込 | LCP、転送量、問い合わせ率 |
| ページ別プレビューにすると共有時の誤認が減る | 地域別OG画像 | 共有時表示、参照流入、CTR |
| 問い合わせへ初回流入情報を付けると、施策別の成果を比較できる | first touch、UTM、referrer | 流入元別問い合わせ数・率 |
| Bingへ更新を通知すると、更新検出が早まる | IndexNow | クロール、Bing表示、AI引用 |
| 旧ドメインを301移行すると、旧LPの評価を集約できる | 旧URL→対応する新URL | 旧URL残存、新URL表示、被リンク継承 |

## 実施した補強

### 全6ページの検索意図を明確化

トップのH1を「北海道の民泊清掃」を明示する内容へ変更しました。

札幌、千歳、小樽、北広島、恵庭のH1には、それぞれの地域名を追加しました。

変更前は地域名をH1に含む地域ページが0件／5件でしたが、変更後は5件／5件です。

title、description、canonical、robotsは既存の良好な設定を維持しました。

### 地域固有の可視FAQを追加

全6ページに4件ずつ、合計24件のFAQを追加しました。

トップでは、対応地域、依頼できる業務、最低料金、リネンの利用方法を説明しています。

地域ページでは、単純な地域名差し替えを避け、次の内容を地域ごとに変えました。

- 対応地区
- その地域へ清掃体制を供給できる理由
- 地域固有の施設・需要・支店情報
- 料金と概算条件

FAQは検索エンジン専用ではなく、利用者が実際に判断するための可視本文として実装しました。

2026年5月にGoogleのFAQリッチリザルトが廃止されたため、検索結果の装飾を狙ったFAQPage構造化データは追加していません。

### 構造化データを事業実態に合わせて再設計

変更前は、地域ページごとに別のLocalBusinessが存在するような記述でした。

変更後は次の関係へ統一しました。

```text
株式会社Stayble（Organization）
└─ WindWoods（Service）
   ├─ 札幌市へ提供
   ├─ 千歳市へ提供
   ├─ 小樽市へ提供
   ├─ 北広島市へ提供
   └─ 恵庭市へ提供
```

各地域ページでは、同じOrganizationをproviderとして参照し、そのページのServiceに対象市を `areaServed` として設定しました。

料金表は1R、1LDK、2LDK、3LDK、戸建ての5種類をOfferCatalogとして記述しました。

本文にない情報、架空の店舗、架空の住所、未確定の電話番号や営業時間は追加していません。

### ページ別OG画像を作成

黒とブランドゴールドの共通デザインで、次の6画像を作成しました。

- 北海道全体
- 札幌
- 千歳
- 小樽
- 北広島
- 恵庭

各画像には地域名、サービス名、地域固有の補足、会社全体の実績であることを明記した数字を配置しました。

### 画像と初期表示を軽量化

## 残っている最重要課題

### 旧ドメインの301リダイレクト

最低限、次の恒久転送が必要です。

```text
https://ww-sapporo-minpaku.com/
→ HTTP 301
https://windwoods-stayble.com/sapporo/
```

HTTP／HTTPS、wwwあり／なしの全入口を対象にします。

旧サイトに他のURLが存在した場合は、旧Search Console、過去sitemap、外部リンク、アクセス解析から一覧を取得し、内容が最も近い新URLへ1対1で転送します。

無関係な旧URLをすべて新トップへ送ると、soft 404として扱われる可能性があります。

Wixを解約済みでWix側に転送を維持できない場合は、旧ドメインのDNSを、Cloudflare Redirect Rulesや同等の301対応サービスへ向ける方法があります。

DNSと旧ドメインの設定は、サイトリポジトリだけでは実施できません。

AI検索は自社サイトだけでなく、会社サイト、ビジネスプロフィール、業界掲載、ニュース、外部リンクなども参照します。

株式会社Stayble、WindWoods、提供サービス、対応地域、所在地の表記を外部でも統一する必要があります。

# 2. この事例から抽出できる汎用的なSEO・LLMO監査の考え方

## SEOは「設定」ではなく継続的な検証工程

SEOは、title、description、sitemapを置いて完了するものではありません。

少なくとも次の段階に分けて考える必要があります。

1. 発見される：DNS、robots、sitemap、内部リンク、更新通知
2. 取得される：HTTP応答、速度、HTML、画像、JavaScript依存
3. 理解される：H1、本文、会社・サービス・地域の関係、構造化データ
4. 選ばれる：検索意図との一致、独自情報、信頼、地域性、比較可能な条件
5. 行動される：表示速度、料金、FAQ、問い合わせ導線
6. 測定される：Search Console、Bing、問い合わせ、流入元
7. 改善される：7日、14日、28日、季節単位で差分確認

どこか一つが欠けると、「インデックスはされているが順位が付かない」「順位はあるが問い合わせがない」「問い合わせはあるが施策を評価できない」という状態になります。

## SEOの点数と検索競争力を混同しない

Lighthouse SEO 100は、基本的な技術要件を満たしていることを示します。

競合より有用であること、地域で信頼されていること、旧サイトの評価を継承していること、検索結果で最上位になることまでは示しません。

技術的な合格と、検索市場での競争力は分けて評価します。

## LLMOはエンティティと事実の一貫性

LLMOを、AI向けファイルを置く作業だけで考えないことが重要です。

AI検索が理解しやすいサイトには、次の特徴があります。

- 誰が運営しているかが明確
- 何というサービスかが明確
- 何を提供するかが本文にある
- どの地域に提供するかがURLと本文で一致する
- 料金と条件が見える
- FAQが利用者の言葉で書かれている
- 構造化データが本文と一致する
- 自社の複数サイトや外部情報で表記が一致する

構造化データや `llms.txt` は、本文にない事実を作り出すものではありません。

## 構造化データは事業実態を模式化する

地域ページが複数あるからといって、すべてをLocalBusinessにするのは適切ではありません。

実店舗型なのか、出張型なのか、1社が複数地域へ提供するのか、地域ごとに本当に別拠点があるのかを確認します。

構造化データは検索キーワードを増やす箱ではなく、現実の会社、サービス、場所、料金の関係を機械へ伝えるものです。

## 地域ページはdoorway化させない

地域名だけを差し替えたページを量産すると、利用者価値が低くなります。

地域ページには少なくとも次のどれかが必要です。

- 地域固有の需要や課題
- 実際の対応地区
- その地域へ供給できる理由
- 支店や物流などの事実
- 地域固有施設との関係
- 地域利用者が尋ねるFAQ

数字や実績を地域別に見せたい場合も、裏付けがなければ会社全体の実績と明記します。

## ドメイン移行は新サイトだけでは完了しない

新ドメインが200で表示されても、旧ドメインが404なら、検索移行は完了していません。

確認すべき入口は次のとおりです。

- HTTP
- HTTPS
- wwwあり
- wwwなし
- 旧トップ
- 旧下層ページ
- パスとクエリの保持

転送はHTTPステータスだけでなく、最終到達先が意図した新ページかを確認します。

## ページ速度はSEOとコンバージョンの共通基盤

重い画像、外部フォント、初期表示に不要な予約・チャット・計測スクリプトは、検索流入後の体験を悪化させます。

優先順位は次のように考えます。

1. LCP画像を軽量化する
2. 画面幅に応じた画像を配信する
3. LCP画像をHTMLまたはpreloadで早く発見させる
4. ファーストビューに不要な画像を遅延読み込みする
5. 問い合わせ後しか使わない外部サービスは、その時点で読み込む
6. 外部フォントの価値と速度コストを比較する

平均点だけでなく、LCP、転送量、TBT、CLSを個別に見ます。

## OGPは順位施策と役割を分ける

OG画像の改善を、直接的な順位上昇として評価しません。

OGPの役割は、共有時の内容一致、ブランドの統一、クリック前の誤認防止です。

順位への効果を主張せず、共有流入やクリック後の信頼性として評価します。

## FAQは検索装飾ではなく意思決定支援

FAQリッチリザルトがなくなっても、FAQ本文の価値は残ります。

利用者とAI検索の双方が、料金、地域、条件、提供範囲を短時間で理解できます。

FAQを追加するときは、検索語を不自然に繰り返すのではなく、問い合わせ前に実際に生じる疑問へ答えます。

## 流入とコンバージョンを同じ線上で見る

検索表示が増えても、問い合わせが増えなければ事業成果とは言えません。

一方で、問い合わせだけを見ても、自然検索、広告、紹介、直接流入のどれが効いたか分かりません。

最低限、次の情報を意味のあるコンバージョン時だけ記録します。

- first landing page
- first area
- referrer
- UTM
- ad click ID
- conversion date

ページ閲覧や概算試行をすべて外部送信すると、データ量が増える一方で、問い合わせとの関係が見えにくくなります。

## 改善前の基準値を必ず保存する

変更前の数字がなければ、改善後に良くなったか判断できません。

最低限保存するものは次のとおりです。

- 測定日
- コミットまたは公開日
- 対象URL
- 検索語サンプル
- Lighthouse条件と結果
- Search Consoleの対象期間
- 問い合わせ数
- 外部施策の実施有無

前後で測定条件が異なる場合は、その違いも明記します。

## 順位だけで良否を決めない

月次評価では、少なくとも次を分けます。

- 指名検索と非指名検索
- 表示回数とクリック
- CTRと平均掲載順位
- モバイルとPC
- 地域ページ別
- 問い合わせ数と問い合わせ率
- AI検索の引用
- 旧ドメイン移行やGBPなど外部施策

季節性の強い事業では、前28日だけでなく前年同期も可能な範囲で確認します。
